# 系统菜单性能与批量传递：0.4.2

本文件为阶段性验收记录。当前行为见[使用说明](../usage.md)。测试文件清单、播放器导出的实际路径和原始日志仅留在本地忽略目录。

## 两类问题

搜索和全选读取索引或查询快照；系统菜单则需要通过 SMB 创建真实 Shell 文件对象，再加载机器上安装的菜单扩展。一次 2,935 项选择分散在 1,592 个目录中，重复解析共享路径与父目录带来大量网络元数据请求。

用户还报告 PotPlayer 只收到前 50 项。本机注册的 Enqueue 命令使用 COM DropTarget；按微软的多选模型，这类命令默认没有 50 项限制。独立的跨目录 60 项选择能完整加入，未证实固定的 50 项上限或宿主提前释放假说。

进一步用一个含 252 个视频、25 条长路径的目录对照，确认旧 `CF_HDROP` 文件清单接口无法完整生成，菜单虽能出现，播放器接收仍会失败或不完整。0.4.1 对 Shell 项目数组与 Copy as path 的兼容没有覆盖这条通道。此次补齐通用文件清单之后，同一个 PotPlayer 菜单能接收全部 252 项。“恰好 50”未被定位为某个固定常数，不将其描述为播放器硬上限。

## 修改

- 在一次准备过程中缓存父目录及各级祖先的 Shell 对象，按相对文件名解析；去掉逐文件的文件系统 canonicalize 和重复的完整路径绑定。
- 跨目录仍使用真实结果文件夹；不可见视图使用列表模式并关闭重绘，避免为不可见的详情列做额外工作。
- 含长路径时，通过 `SHCreateDefaultContextMenu` 的原生回调向数据对象补入完整 UTF-16 `CF_HDROP` 清单；保留其余原生格式、文件关联和命令执行。初始化失败不显示部分菜单。
- 没有新增文件数量限制、辅助进程或应用专属执行逻辑；准备提示仍未恢复。

## 耗时对照

同一 Windows 主机和局域网，使用冻结的 0.4.1 源码与本次实现分别运行调试构建。以下为单次测量，缓存与网络状态会影响绝对值；不把它们当成稳定性能保证。

| 2,935 项的阶段 | 0.4.1 | 0.4.2 |
|---|---:|---:|
| 准备 Shell 文件对象与结果集合 | 28.25 秒 | 4.32 秒 |
| 生成应用菜单 | 9.87 秒 | 13.99 秒 |
| 合计 | 38.12 秒 | 18.30 秒 |

新版向扩展提供了此前失败的完整文件清单，扩展阶段处理更多内容，耗时有所增加；总耗时仍减少约一半。252 项目录的准备对象阶段从约 2.4 秒降到约 0.34 秒，完整菜单准备约 1.7 秒。该目录从 NAS 读取全部选择路径的请求仅约 19 毫秒，查询本身约 0.7 秒。

## 验证

- 原生菜单库：10 项通过，1 项真实环境测试默认跳过；额外显式执行 252 项真实环境测试通过，同时检查 Shell 项目数组与完整 CF_HDROP 内容。
- PotPlayer 实际列表从 230 项增到 482 项；读取其保存的播放列表核对，目标 252 项全部存在，包括 25 条长路径，没有路径截断。
- 客户端 Rust：11 项通过，2 项依赖环境的测试默认跳过。
- 0.4.2 发布构建成功，已安装并保留现有连接配置。
- 安装后在客户端实际全选 252 项，执行系统菜单的 PotPlayer Enqueue；验证专辑由 1 项增至 253 项。读取该专辑保存文件再次核对，目标 252 项零遗漏，25 条长路径完整。

## 后续体验取舍

大批量原生菜单仍可能等待十几秒。进一步改善体验可将文件对象准备移到后台，超过约一秒再在状态栏显示进度；快速完成的小选择不显示提示。后台方案需要保持 Shell 对象与菜单线程的生命周期正确，不能直接跨线程传裸 COM 对象。

针对成千上万个媒体文件，通用 M3U8 播放列表导出更直接：从查询快照生成路径清单，交给关联播放器打开，省去加载所有文件的系统菜单。该功能本次仅提出，没有实现。
